The Speaker Loop

22 sessions, booked without a spreadsheet

One source of truth, a generated application form, and a board that knows whether the calendar invite was accepted.
The clearest end-to-end loop in the system: a date in a source file becomes a form choice, an application, a booking, a printed brief and a published event.
The problem

Twenty-two dates, and nobody to fill them

The programme promises founders a session roughly twice a week for eight weeks. Twenty-two slots, each needing a speaker, a title, a description, a published event page and a one-pager brief. Applicants were promised an answer within one business day.

Done by hand that is a spreadsheet of dates, a second spreadsheet of people, an inbox, a calendar, and a running fear that two speakers have been offered the same Friday. The interesting part is not the booking. It is keeping five systems agreeing about what a date is.

End to end

The loop, in seven links

1
Source of truth

lib/edu-sessions.js

Twenty-two sessions, each a number, a day, a time and a Luma slug. Everything downstream reads this file. Sessions 17 and 18 are both Tue Oct 20 at 5:30 on purpose, two rooms in the same hour, and the file says so in a comment so nobody helpfully deletes the duplicate.

2
Generated, not hand-built

scripts/create-speaker-form.mjs

Builds the "Speak at Uplift" Typeform over the API, turning each session into a dropdown choice via sessionLabel(). Re-run it with the form id and a schedule change pushes into the live form. Nobody edits twenty-two dates by hand in a form builder.

3
Outside the system

The applicant picks three ranked dates

Plus a title, what they would cover, three takeaways, a bio, who it is aimed at, and whether they are open to running a series. There is also an "any of these work" option, which turns out to be the most useful answer anyone gives.

4
Read live

pages/api/admin/speaker-applications.js

Fetches the form definition and the responses together. Typeform keys answers by field id, so the definition is what turns them back into named fields. Chosen date labels go through sessionNumberFromLabel() to become slot numbers, then decisions from the FallSpeakers sheet tab are overlaid. Sixty-second cache, ?fresh=1 to bypass.

5
Human decision

The slot board, and speaker-decide.js

Four decisions: approved, pending, rejected, clear. Pending holds the slot exactly like an approval does, so a date offered to someone awaiting reply cannot be offered to anyone else. The sheet is append-only and the latest row per applicant wins, so a reversal is a new row rather than an edit.

6
Generated artefact

The one-pager brief

One page per speaker, anchored by slug, rendered from HTML to PDF. It is what the speaker gets, what the host reads before introducing them, and what goes out with the event.

↓
7
Published

The Luma event

Title and description land on the event page founders register through. Attendance comes back the other way, into the milestone that says a founder completed three educational sessions. The loop closes.

The interesting bit

A string is the join key between two systems

Change the date format and approved speakers silently stop mapping to slots

The date a speaker picked is stored by Typeform as the text of the choice they clicked. Not an id. Text. So sessionLabel() is not a display helper, it is the contract between the app and every response already sitting in the form.

Reformat it, even harmlessly, and sessionNumberFromLabel() starts returning null for every historical response. Nothing throws. The board just quietly shows speakers as having picked no date, and the slots they were holding come free.

You cannot fix it forward either, because the responses are already submitted. The file carries the warning in a comment above the function, which is the only enforcement a two-system string contract really gets.

// sessionLabel() must keep producing the exact strings used as date choices in
// the live speaker Typeform (uUjnsoDm), or approved speakers stop mapping to
// slots. Re-run the form script after changing it.

export const sessionLabel = (s) => `Session ${s.n} · ${s.day} · ${s.time} ET`;

// "Session 7 · Fri Sept 25 · 12:30 PM ET" -> 7. Returns null for the
// "Any of these work" choice and for anything unrecognized.
export function sessionNumberFromLabel(label) {
  const m = /^Session (\d+)\b/.exec((label || "").trim());
  if (!m) return null;
  const n = parseInt(m[1], 10);
  return EDU_SESSIONS.some(s => s.n === n) ? n : null;
}

One click, four systems

What confirming a speaker actually sets off

Pressing Confirm & book does one thing: it writes the booking and takes the date off the board for everyone else. Three more things then have to happen in three different places, and none of them are the same act as booking.

The interface says so itself, directly under the link to the application form, so nobody mistakes a booking for a confirmation:

"Share this with anyone who wants to speak. Approving here books the slot; the Luma event title and the invite are still yours to send."

That sentence is a design decision, not a caveat. A system that fires all four and assumes they worked is a system where a speaker turns up to an event that was never published, or does not turn up because the invite went to an address nobody reads. So the booking is automatic, each remaining step is cued with whatever can be pre-filled, and the board's real job is knowing which of the four actually happened.

Automatic

The booking

Written to the FallSpeakers sheet, append-only, latest row per applicant wins. The slot is now held and cannot be offered twice. This is the only step the click performs.

The confirmation email

Approving puts a compose button on the row with the subject already written: "You're speaking at Uplift, Session 7." It opens a draft; it does not send. The board then carries confirmationEmailSent as a date, so booked-but-unemailed and emailed-but-unbooked are visibly different states rather than both reading as green.

3
Tracked, sent by a person

The calendar hold

Two fields, not one: calendarInviteSent and inviteResponse. Sending a hold and having it accepted are different facts, and the gap between them is the single best predictor of a no-show. "Invite sent, no reply" is the state worth chasing, and it is invisible to anything tracking only booked or not booked.

↓
4
Scripted, run by a person

The brief, then the Luma event

The one-pager is generated, but not from the application on its own: an approved speaker is added to the roster file and build-session-briefs.py re-run. Until that happens the console says exactly what is wrong, in its own words: "The slot is booked and the event page has nothing to publish." Session copy then goes to Luma, and registration counts come back the other way into the console.

The read that lied, and the fix that matters more than the feature

Reading registration counts back from Luma broke twice, and both times it surfaced as "the onboarding bookings stopped working".

First, the console asked Luma for thirty-odd guest lists at once. Luma rate-limits, the calendar listing itself came back 429, and the listing loop treated a non-ok response as the end of the data. An empty calendar matches no events, so every session read "not on Luma" and every count read zero.

Then those zeros were cached for five minutes and served as fact. A failed read is now never cached and never rendered as a number. The payload says it failed and the screen says so too, because nothing about this programme should be measured by "we could not reach Luma" quietly meaning "nobody came".

Designed, not yet shipped

Collapsing the four into one

Every one of those three manual steps is a place a speaker falls through, and the board exists to catch that rather than to prevent it. Catching it is the interim answer. The next version makes Confirm & book do the whole thing.

Why it was not built that way first

Because the failure states had to be understood before they could be removed. Building the automation first would have produced a system that fires four actions and assumes all four worked, and the interesting information, the gap between a hold being sent and a hold being accepted, would never have been visible at all.

The board earned the automation by making the failures countable first. That is also why the fields survive the change: confirmationEmailSent, calendarInviteSent and inviteResponse still record what happened, they just stop depending on a person to write them down.

What the design missed

The form was the plan. Email was what happened.

An invite went out to around eighteen mentors asking them to speak. Several replied straight to my inbox with a bio, a topic, takeaways and their available dates. They never touched the form, so the admin could not see them at all.

The Speakers tab reads the Typeform. That was the entire design, and it was correct right up to the moment a real person answered an email instead. Eighteen of the most likely speakers in the programme were invisible to the system built to track speakers.

The fix is not clever, and I think that is the point. A roster file carries the people who came in by email, each marked source: "email", alongside the ones the form knows about. It is hand-maintained, which is a real cost, and the file says so at the top so the next person knows what they are inheriting rather than discovering it.

// This exists because the Speakers tab could only ever see the Typeform
// (uUjnsoDm). The Aug 28 invite email went to ~18 mentors and several replied
// with bio, topic, takeaways and dates straight back to Kennedy, never touching
// the form, so they were invisible in the admin. Those people are marked
// source: "email" below and there is no other record of them in the app.
//
// A row here does NOT book the slot. Booking still happens through
// /api/admin/speaker-decide, which writes the FallSpeakers sheet.

Two intake paths, one board. The comment matters more than the code: it records that the second path is a patch over a design assumption, not a feature, so nobody later mistakes the hand-maintained file for the intended architecture.

The far end

What the founder finally sees

The published event. Title and description come from the application, the date from the source file, and registration comes back as attendance against the founder's three-session requirement.

And the brief that goes with it, one page per speaker, generated from the roster. There is a plain-language write-up of the whole system as well, for whoever runs it next.
